1. The Race Condition (Phase 2):
In the `race_condition.py` script, what exactly causes the final weight to be less than the expected value? Explain the role of the OS Scheduler in this error.
Answer:
- The error is caused by non-atomic operations (Read -> Modify -> Write) on the shared variable `shared_weight`.
- The OS Scheduler performs Context Switching (preemption) while a thread is paused at `time.sleep()`. 
- Both threads end up reading the same stale value from RAM before either can write back the incremented value. As a result, one thread's update overwrites the other (Lost Update problem), making the final value lower than 200.

2. Mutex vs. Semaphore (Phase 3):
In `producer_consumer.py`:
- What is the specific job of the `mutex`?
- What is the specific job of the `empty` and `full` semaphores? 
(Why can't we just use a Mutex for everything?)
Answer:
- Mutex (`threading.Lock`): Ensures Mutual Exclusion. It guarantees that only ONE thread (Producer or Consumer) can enter the critical section to access/modify the shared buffer and index pointers (`in_index`, `out_index`) at any given time.
- Semaphores (`empty` and `full`): Used for Signaling and Resource Counting. `empty` tracks available empty slots (starts at 5), while `full` tracks filled data slots (starts at 0).
- Why Mutex isn't enough: A Mutex only provides lock/unlock capabilities for code sections; it cannot keep count of available resources or automatically suspend threads when the buffer is empty or full.

3. Deadlock Awareness:
In the Producer function, we wrote:
    empty.acquire()
    mutex.acquire()
What would happen if we swapped these two lines? (mutex first, then empty). Imagine the buffer is completely full. Explain the potential OS problem.
Answer:
- Swapping the lines causes a DEADLOCK when the buffer is full.
- Scenario:
  1. The Producer acquires the `mutex` lock first.
  2. The Producer then calls `empty.acquire()`. Since the buffer is FULL, `empty` count is 0, so the Producer is put to SLEEP while still holding the `mutex`.
  3. The Consumer tries to run to read data and free a slot, but it gets BLOCKED at `mutex.acquire()` because the Producer is holding the lock.
- Result: Both threads are permanently stuck waiting for each other (Deadlock).
